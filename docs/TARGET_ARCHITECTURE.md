# 建議目標架構

**狀態：每資料夾可攜記錄、共用值預設及 SQLite 可重建索引已核定；實體格式仍待設計。** 使用者要求跨專案搬移後可直接看到資料夾原值，目的專案只決定顯示；徹底清理後搬移的資料夾依 C-66 視為全新。具體 POC 分層與選型見 [POC 技術架構](POC_TECH_ARCHITECTURE.md)，資料規則見 [資料夾與專案模型](FOLDER_PROJECT_MODEL.md)、[儲存與清理](STORAGE_OPTIONS.md)。現有程式碼是研究原型，不能直接作為資料模型或 UI 架構範式；目前程式事實見 [ARCHITECTURE.md](ARCHITECTURE.md)，尚待決定的細節見 [OPEN_DECISIONS.md](OPEN_DECISIONS.md)。

## 建議的資料責任

```text
來源資料夾樹（可攜、可復原的真實資料）
  ├─ 每個資料夾的隱藏記錄：folder ID、共用有型別屬性、顯式專案私有覆寫
  ├─ 專案根目錄的專案定義：project ID、欄位映射、分類、掃描規則、版面
  └─ 可攜圖片資產：以相對引用連接
                    ↓ 掃描、驗證、建立索引／修復
本機 SQLite（可重建的索引與查詢模型）
                    ↓ 分頁、篩選、排序
Electron main / preload → React + Vite 畫面
```

資料夾記錄與專案定義作為可攜的權威資料，SQLite 作為本機索引，這項分工已核定。SQLite 可對專案、資料夾、欄位值建立索引，支援大量資料的查詢和分頁；是否真的更快、需要哪些索引，仍須用代表性資料量測。SQLite 的索引和全文搜尋能力有官方文件；WAL 能改善讀寫並行，但 SQLite 官方說明它不適合讓不同主機共用同一個 WAL 資料庫，因此本機 SQLite 檔不作跨設備同步格式。[SQLite 索引](https://www.sqlite.org/lang_createindex.html)、[FTS5](https://www.sqlite.org/fts5.html)、[WAL](https://www.sqlite.org/wal.html)

## 資料模型：先分清「值」與「顯示」

| 概念 | 建議責任 |
| --- | --- |
| Folder | 實際資料夾；有穩定 folder ID。當前路徑與檔案系統名稱由掃描取得，不用舊設備的絕對路徑作身分。 |
| Project | 以某資料夾為根，定義掃描規則、欄位、版面、每列數量與分頁大小；巢狀專案可重疊。 |
| Field definition | 共用屬性以穩定 ID 與型別識別；專案保存其查詢別名、欄位映射和顯示名稱。同名別名不推定為同一屬性。 |
| Field value | 資料夾自身攜帶可跨專案讀取的有型別值，建議以 folder ID＋屬性 ID 識別；只有顯式建立的專案私有覆寫再加 project ID。確切格式待設計。 |
| Renderer / layout item | 引用 field ID，決定文字、數字、標籤、圖片等如何顯示及排列；不直接定義值的身分。 |
| Action | 例如「開啟此資料夾」是核定的動作及其設定，不必偽裝成資料欄位值；任意外部命令另議。 |

POC 先顯示系統名稱、目前路徑及基本文字 cell，驗證完整功能閉環；MVP 逐步增加其他顯示與操作，具體型別尚待後續討論。系統產生的資料夾名稱與路徑不當作舊設備可攜的絕對路徑；自訂名稱是獨立值，不覆寫實際資料夾名稱。現有 `shared/main.ts` 的 `DataType` 聯集不是目標範式；型別擴充需定義舊值轉換規則。

## 建議的寫入與復原流程

1. 選根資料夾，掃描指定層級；每個納入範圍的資料夾讀取或建立隱藏記錄。分析階段先取得目錄結構與基本系統欄位；更深入的媒體分析另定範圍。
2. 在資料夾記錄中保存 folder ID、有型別且可跨專案讀取的欄位值及來源，必要時另存顯式專案私有覆寫；專案根設定保存分類、欄位映射、renderer、排列、掃描及列表設定，不因資料夾搬入而改寫其原值。圖片原檔複製到該資料夾的可攜資產區並用相對路徑引用；縮圖可以作本機快取。精確 schema 待設計。
3. 編輯單筆資料時先驗證型別與路徑，再可靠寫入可攜檔，最後更新 SQLite。兩種儲存無法天然形成同一個交易；若中途失敗，下次以可攜檔重新核對並修復索引。具體檔名、寫入方法及回復政策仍待決議。
4. 新設備先掃描資料樹、讀取專案定義與各資料夾記錄，再重建本機 SQLite。即使索引不存在，也要能復原欄位值、版面和圖片。
5. 複製資料夾會連 ID 一起複製，與唯一性要求衝突。偵測到兩份同 ID 時，不默默合併或覆寫；保留資料並依核定政策處理副本。

## 查詢與呈現

列表設定屬專案，不屬單一資料夾。POC 需要可設定每列資料夾筆數（例如 2）及每頁資料夾筆數（例如 100）；每頁先取得符合掃描規則的資料夾集合，再以穩定排序分頁，讓重開或切頁結果可預期。單筆資料編輯與版面編輯是兩個不同操作：前者改該資料夾的值，後者改整個專案的 renderer 和排列。

搜尋方案 A 已核定：單一搜尋框、欄位提示、按 key/value 組合及當前專案無 key 搜尋。文字須匹配任意子字串。建議讓 UI 傳遞經解析與驗證的查詢條件到 main process，SQLite 以可重建索引執行；欄位身分仍用 field ID，不把使用者輸入的 key 當 SQL 名稱。短於三個 Unicode 字元與大量資料的效能另需測試，詳見 [SEARCH_DESIGN.md](SEARCH_DESIGN.md)。

積木式 cell 編輯器可先以 `react-grid-layout` 作格線拖放、縮放引擎；自己的版面模型保存組件、資料綁定及樣式，清單以唯讀模式呈現。細部規則見 [EDITOR_DESIGN.md](EDITOR_DESIGN.md)。

程式內保存成功後，main process 回傳已保存的最新資料；renderer 立即更新當前項目、清單與搜尋結果，再按需要重新查詢受影響頁面。保存失敗時顯示錯誤並回復未完成狀態。外部程式修改資料後，在視窗重新聚焦或手動重新掃描時同步。

動作採可擴充的型別與參數模型，POC 先實作「開啟目前資料夾」。新增控制電腦的動作時，由 main process 對各動作驗證參數及執行權限；不要讓 renderer 直接傳任意命令給作業系統。Electron 官方建議 preload 僅暴露明確的 IPC 方法。[Electron context isolation](https://www.electronjs.org/docs/latest/tutorial/context-isolation)

## 主要取捨與風險

- 每資料夾隱藏檔利於搬移與復原，但首次掃描須讀許多小檔，且來源可能唯讀或被其他程式更動。SQLite 只能加速已索引資料，不能代替首次掃描或可攜檔的正確性。
- 專案根定義與每資料夾記錄分開，便於共用一個資料夾於多個專案；也需要規定只搬移子樹、專案根記錄遺失時的行為。
- 固定值型別讓查詢與 renderer 驗證容易；完全任意 JSON 彈性高，但型別轉換、排序和跨設備相容更難。建議先以少數明確型別驗證 POC。
- SQLite 是否採 WAL、FTS 或哪些索引，應由實際查詢與資料量決定；它們是後續優化手段，不是產品資料契約。
