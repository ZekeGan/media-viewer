## 入口與資料流

```text
Electron main (electron/main.ts)
  ├─ JsonStorage(app.getPath('userData'))
  ├─ FolderSyncService → 掃描資料夾
  ├─ ViewService → 組合 View／Folder／Column／Layout
  └─ IPC ← preload 的 window.electronApi
                   ↑
Next.js / React renderer (src/app/view、src/app/editor)
  └─ Zustand stores → 檢視與編輯畫面
```

- `electron/main.ts` 固定載入 `http://localhost:3000/view`。`electron.vite.config.ts` 只建置 main 和 preload；renderer 由 Next.js 處理。
- `electron/preload.ts` 暴露建立、列出、讀取與儲存視圖，以及選取資料夾的 API。`electron/ipc/` 接到 services。
- `electron/services/folderSyncService.ts` 遞迴掃描資料夾。`ViewService` 產生預設欄位與版面，讀取時組合各種資料。
- `electron/storage/JsonStorage.ts` 目前把資料寫在 Electron `userData/app-data`，**尚未在每個來源資料夾寫隱藏記錄**。
- `shared/main.ts` 定義 View、Folder、Column、Layout、Cell。`src/hooks/useLoadInitialData.ts` 將資料載入 Zustand；`src/app/view/page.tsx` 依版面顯示清單；`src/app/editor/` 是尚未完成的編輯器。

## 已知落差與待修正點

- 現有 `View` 接近產品所說的專案，但兩者資料契約尚未正式對齊。`Column` 以全域 `key` 儲存、`Cell` 只帶 `key`，不能安全表達重疊專案的同名異型別欄位：`shared/main.ts`、`electron/storage/JsonStorage.ts`。
- `getAllFolders()` 以 `for ... in` 遍歷檔名陣列，組出索引數字作檔名：`electron/storage/JsonStorage.ts`。
- 建立視圖的 IPC handler 沒有回傳 `service.createView(...)` 的 Promise；畫面建立後也沒有刷新視圖清單：`electron/ipc/view.ts`、`src/app/view/_containers/navBar.tsx`。
- 編輯頁的「儲存」呼叫 `createView('')`，表單以 view ID 查 layout，且編輯器渲染器未取得必要的 cells：`src/app/editor/page.tsx`、`src/app/editor/_containers/editArea.tsx`、`src/components/layoutItem/index.tsx`。
- `JsonStorage` 的 layout item 方法仍拋出 `Method not implemented`。SQLite 尚未實作：`electron/storage/JsonStorage.ts`、`package.json`。
- `PLAN.md` 與 `_abandon/` 保留舊構想及舊程式碼，不用來判定目前功能是否完成。

## 遷移方向（尚未執行）

## 實體契約與復原

每個受管資料夾有 `.media-viewer/folder.json`（kind、schemaVersion、folderId、revision、attributes、assets、projectOverrides）。Windows 根建立時設隱藏，子項在掃描收尾批次設定；取消也會處理已完成項目，失敗回報並重試。圖片複製至 `assets/<assetId>.<ext>`；專案根內的 `projects/<projectId>.json` 保存模板、欄位綁定、掃描與列表設定。本機 `poc-projects.json` 只記根位置與 projectId。完整格式以 `shared/model.ts` 為準。

保存採暫存檔、同步寫入、`.bak` 與置換，revision 或內容變更時拒絕覆蓋。初次寫入也建立基準備份。損壞的單筆可由詳情恢復，失效專案有根／設定復原入口，原損壞檔另存 `.damaged`，有效備份保留。這些未知／損壞副本不自動刪除。清理全部只涵蓋已連結、可存取且可驗證歸屬的記錄；離線根、未連結副本及舊資料備份需另外處理。

- 遊戲專案辨識到遊戲 ROOT 後停止深入；其他分類遇疑似遊戲需提示。C-80 採候選辨識＋人工修正與集中處理，納入 Unity、RPG Maker、Unreal、Godot 及其他家族的 [辨識規畫](../GAME_ENGINE_DETECTION.md)；組合規則及人工 ROOT 已實作，所有引擎版本仍待實機樣本。ROOT 保留自身可攜目錄，內部不新增記錄或改動遊戲檔；繼續查看採唯讀設計。精確第 N 層不因較淺的遊戲邊界例外列出，須提示停止原因。見 [遊戲檢視設計](../GAME_VIEWER_DESIGN.md)。

- 支援「顯示第 1 至 N 層」與「只顯示第 N 層」，例如顯示第 1、2、3、4 層或只顯示第 4 層。根資料夾在使用者設定中算第 1 層；精確模式仍須走訪父層。
- 巢狀專案可以重疊。例如 `/1` 的專案 1 與 `/1/1/2` 的專案 2 都可顯示同一資料夾；資料夾共用原值可跨專案讀取，各專案可用不同 renderer／版面。確實需要不同值時可顯式建立專案私有覆寫。
- 每個資料夾都要建立唯一、隱藏、可攜的記錄；換設備且沒有本機資料庫時，仍可復原資料與專案內容，並在新設備重新自訂顯示。
- 自訂圖片複製到可攜資料範圍並以相對路徑引用，隨資料夾復原。
- 儘早將目前 Next.js 畫面層改為 React + Vite；Electron main／preload／IPC 保留各自職責。
- SQLite 是由可攜資料重建的本機索引，已加入。1,000 筆暖機搜尋 200ms 目標的本機查詢基準已測；不以主程序 SQL 時間代表完整 UI 延遲，實測見 STAGES_2_3。
- 欄位值、renderer、cell 排列及動作分開建模；專案、資料夾與欄位使用穩定 ID，同名 key 不推定為同一型別。資料夾共用值為預設、專案私有覆寫須顯式建立；舊的所有值按專案隔離規則已被取代，見 [資料夾與專案模型](../FOLDER_PROJECT_MODEL.md)。資料夾搬移保留 ID；複製衝突須偵測、保留資料並明確處理。
- 程式內保存資料、版面或列表設定後，畫面立即更新，無需重開程式。
- POC 自動分析目錄結構、資料夾名稱與目前路徑；檔案數、封面推斷及其他媒體資訊後續逐項增加。程式外部變動於重新聚焦視窗或使用「重新掃描」時同步。
- 第一版以 Windows 驗收；同一根資料夾允許多個獨立專案。唯讀資料夾可檢視既有資料，寫入失敗必須明確提示，不改存本機。
- POC 按鈕先提供「開啟目前資料夾」；動作模型保留未來新增其他控制電腦功能的擴充性。跨設備先支援單向複製與復原，版本衝突時保留資料並提示。
- 搜尋要能依專案欄位 key 與值組合查詢；使用者忘記 key 時仍能搜尋。基本語法已核定；優先順序與索引行為見 [SEARCH_DESIGN.md](../SEARCH_DESIGN.md)。
- 搜尋採單一搜尋框、欄位提示與無 key 自由文字；無 key 先搜尋當前專案名稱、路徑、文字與標籤。任意一段文字相符都應可找到。基本語法採同 key 逗號 AND、空格 AND、引號、排除與單層 OR；特殊字元跳脫細節待定。約 1,000 筆作 POC 基準，不設資料模型硬上限。
- 查詢別名在專案內不分大小寫且唯一；顯示名稱可以不同或重複，欄位身分仍由固定 ID 決定。
- 只顯示第 N 層時，所有實際走訪的祖先資料夾也建立記錄。保存圖片原檔於該資料夾的可攜資產區；縮圖可作本機快取。使用者希望日常使用時感覺不到這些隱藏記錄。
- 積木式版面編輯是核心功能：從左側選組件拖到畫布，調整位置與長寬、文字和背景顏色等，組成每個資料夾卡片的顯示模板。新專案先有預設版面，使用真實資料夾名稱／路徑預覽；固定邏輯格線、樣式設定、數值定位、取消及多步復原／重做已核定。詳見 [EDITOR_DESIGN.md](../EDITOR_DESIGN.md)。
- 約 1,000 個資料夾是 POC 效能基準，不設硬上限；暖機搜尋先以 200ms 內作工程目標，10,000 筆壓力測試，首次掃描另量測。編輯器碰撞自動推開或拒絕；預設卡片有名稱、路徑與開啟按鈕，單筆編輯從列表側欄進入。預設依名稱與穩定 ID 排序、每頁 100 筆；掃描可見進度並可取消、續掃。
- 批次編輯標籤／欄位與保存常用搜尋排在 POC 通過後的 MVP。遊戲商店與 E-Hentai 是外部中繼資料來源候選，第一個網站留到進入該階段時選，詳見 [外部資料設計](../METADATA_ENRICHMENT.md)。
- 媒體分類涵蓋遊戲、漫畫、影片、相簿、音樂；分類決定專案顯示行為，不自動改資料夾屬性。前四種首輪已實作，音樂下一版。第一個來源選 E-Hentai，URL 候選預覽確認後將公開欄位／封面縮圖隨資料夾保存；其他來源後議。
- 層級瀏覽規畫三種視圖：POC 平面清單＋層級篩選；MVP 逐步加入可展開樹／麵包屑和蜂巢／樹圖總覽。
- 搬入目的專案掃描範圍的資料夾應被列出並讀取其自身內容；目的專案缺少的 key 顯示空白或視覺預設，其他原值仍可在詳情查看。媒體分類在專案設定中，不因搬移寫入資料夾；分類明確不符時顯示提示但允許檢視。
- 個別清理區分「本專案資料」及「此資料夾全部本程式資料」；一鍵清理分列可攜與本機資料，報告未連結／離線範圍。
- CELL 可呈現有型別資料與受控操作。POC 已有基本組件；C-85 採 MVP 先圖片／標籤，再按案例加數字／日期，逐項交付；日期精度及其他型別留具體階段。
- 既有資料型別只是早期草案，後續可重設；現有程式碼不是未來架構的範式。使用者曾描述遷移前整體畫面與功能進度不足 50%，屬早期概念 POC。

## 設計目標與例子

- 專案 1 可顯示資料夾名稱、標籤、位置；專案 2 可顯示名稱與自訂按鈕（例如開啟資料夾）。這些是功能例子，不表示所有 renderer 已排入第一版。
- 同名 key 不必代表相同型別。舊的 `projectId + folderId + fieldId` 只能視為先前隔離方案；共用屬性預設用資料夾及穩定屬性 ID 識別，顯式覆寫才帶 project ID，確切 schema 待設計。
- 可攜記錄及專案設定是資料來源；SQLite 可重建。當前同步、錯誤及保存契約見 STAGES_2_3，不再將已實作 schema 列成全部待設計。

## 暫定 POC 驗收方向

先前討論的端到端流程仍重要：指定資料夾 → 分析符合深度設定的資料夾 → 顯示清單 → 自訂 cell 內容與排列 → 編輯單筆值 → 設定每列／每頁 → 保存後立即更新。使用者最新要求 **POC 展示基本功能，MVP 逐步增加其他資料顯示與操作；具體型別後續再談**。POC 以真實名稱／路徑、簡化文字 cell、開啟資料夾、搬移重連及清理驗證這條閉環；依 C-56，見 [CELL 目錄](../CELL_CATALOG.md) 及 [路線圖](../ROADMAP.md)。

搜尋是已確認的目標功能：既可組合欄位 key/value 條件，也可在忘記 key 時輸入一般文字。基本語法及搜尋真實值範圍已核定；POC 先驗證名稱／路徑子字串，完整語法後續交付，見 [SEARCH_DESIGN.md](../SEARCH_DESIGN.md)。

# 建議目標架構

**狀態：每資料夾可攜記錄、共用值預設及 SQLite 可重建索引已核定；實體格式仍待設計。** 使用者要求跨專案搬移後可直接看到資料夾原值，目的專案只決定顯示；徹底清理後搬移的資料夾依 C-66 視為全新。具體 POC 分層與選型見 [POC 技術架構](../POC_TECH_ARCHITECTURE.md)，資料規則見 [資料夾與專案模型](../FOLDER_PROJECT_MODEL.md)、[儲存與清理](../STORAGE_OPTIONS.md)。現有程式碼是研究原型，不能直接作為資料模型或 UI 架構範式；目前程式事實見 [ARCHITECTURE.md](../ARCHITECTURE.md)，尚待決定的細節見 [OPEN_DECISIONS.md](../OPEN_DECISIONS.md)。

## 建議的資料責任

```text
來源資料夾樹（可攜、可復原的真實資料）
  ├─ 每個資料夾的隱藏記錄：folder ID、共用有型別屬性、顯式專案私有覆寫
  ├─ 專案根目錄的專案定義：project ID、欄位映射、分類、掃描規則、版面
  └─ 可攜圖片資產：以相對引用連接
                    ↓ 掃描、驗證、建立索引／修復
本機 SQLite（可重建的索引與查詢模型）
                    ↓ 分頁、篩選、排序
Electron main / preload → React + Vite 畫面
```

資料夾記錄與專案定義作為可攜的權威資料，SQLite 作為本機索引，這項分工已核定。SQLite 可對專案、資料夾、欄位值建立索引，支援大量資料的查詢和分頁；是否真的更快、需要哪些索引，仍須用代表性資料量測。SQLite 的索引和全文搜尋能力有官方文件；WAL 能改善讀寫並行，但 SQLite 官方說明它不適合讓不同主機共用同一個 WAL 資料庫，因此本機 SQLite 檔不作跨設備同步格式。[SQLite 索引](https://www.sqlite.org/lang_createindex.html)、[FTS5](https://www.sqlite.org/fts5.html)、[WAL](https://www.sqlite.org/wal.html)

## 資料模型：先分清「值」與「顯示」

| 概念 | 建議責任 |
| --- | --- |
| Folder | 實際資料夾；有穩定 folder ID。當前路徑與檔案系統名稱由掃描取得，不用舊設備的絕對路徑作身分。 |
| Project | 以某資料夾為根，定義掃描規則、欄位、版面、每列數量與分頁大小；巢狀專案可重疊。 |
| Field definition | 共用屬性以穩定 ID 與型別識別；專案保存其查詢別名、欄位映射和顯示名稱。同名別名不推定為同一屬性。 |
| Field value | 資料夾自身攜帶可跨專案讀取的有型別值，建議以 folder ID＋屬性 ID 識別；只有顯式建立的專案私有覆寫再加 project ID。確切格式待設計。 |
| Renderer / layout item | 引用 field ID，決定文字、數字、標籤、圖片等如何顯示及排列；不直接定義值的身分。 |
| Action | 例如「開啟此資料夾」是核定的動作及其設定，不必偽裝成資料欄位值；任意外部命令另議。 |

POC 先顯示系統名稱、目前路徑及基本文字 cell，驗證完整功能閉環；MVP 逐步增加其他顯示與操作，具體型別尚待後續討論。系統產生的資料夾名稱與路徑不當作舊設備可攜的絕對路徑；自訂名稱是獨立值，不覆寫實際資料夾名稱。現有 `shared/main.ts` 的 `DataType` 聯集不是目標範式；型別擴充需定義舊值轉換規則。

## 建議的寫入與復原流程

1. 選根資料夾，掃描指定層級；每個納入範圍的資料夾讀取或建立隱藏記錄。分析階段先取得目錄結構與基本系統欄位；更深入的媒體分析另定範圍。
2. 在資料夾記錄中保存 folder ID、有型別且可跨專案讀取的欄位值及來源，必要時另存顯式專案私有覆寫；專案根設定保存分類、欄位映射、renderer、排列、掃描及列表設定，不因資料夾搬入而改寫其原值。圖片原檔複製到該資料夾的可攜資產區並用相對路徑引用；縮圖可以作本機快取。精確 schema 待設計。
3. 編輯單筆資料時先驗證型別與路徑，再可靠寫入可攜檔，最後更新 SQLite。兩種儲存無法天然形成同一個交易；若中途失敗，下次以可攜檔重新核對並修復索引。具體檔名、寫入方法及回復政策仍待決議。
4. 新設備先掃描資料樹、讀取專案定義與各資料夾記錄，再重建本機 SQLite。即使索引不存在，也要能復原欄位值、版面和圖片。
5. 複製資料夾會連 ID 一起複製，與唯一性要求衝突。偵測到兩份同 ID 時，不默默合併或覆寫；保留資料並依核定政策處理副本。

## 查詢與呈現

列表設定屬專案，不屬單一資料夾。POC 需要可設定每列資料夾筆數（例如 2）及每頁資料夾筆數（例如 100）；每頁先取得符合掃描規則的資料夾集合，再以穩定排序分頁，讓重開或切頁結果可預期。單筆資料編輯與版面編輯是兩個不同操作：前者改該資料夾的值，後者改整個專案的 renderer 和排列。

搜尋方案 A 已核定：單一搜尋框、欄位提示、按 key/value 組合及當前專案無 key 搜尋。文字須匹配任意子字串。建議讓 UI 傳遞經解析與驗證的查詢條件到 main process，SQLite 以可重建索引執行；欄位身分仍用 field ID，不把使用者輸入的 key 當 SQL 名稱。短於三個 Unicode 字元與大量資料的效能另需測試，詳見 [SEARCH_DESIGN.md](../SEARCH_DESIGN.md)。

積木式 cell 編輯器可先以 `react-grid-layout` 作格線拖放、縮放引擎；自己的版面模型保存組件、資料綁定及樣式，清單以唯讀模式呈現。細部規則見 [EDITOR_DESIGN.md](../EDITOR_DESIGN.md)。

程式內保存成功後，main process 回傳已保存的最新資料；renderer 立即更新當前項目、清單與搜尋結果，再按需要重新查詢受影響頁面。保存失敗時顯示錯誤並回復未完成狀態。外部程式修改資料後，在視窗重新聚焦或手動重新掃描時同步。

動作採可擴充的型別與參數模型，POC 先實作「開啟目前資料夾」。新增控制電腦的動作時，由 main process 對各動作驗證參數及執行權限；不要讓 renderer 直接傳任意命令給作業系統。Electron 官方建議 preload 僅暴露明確的 IPC 方法。[Electron context isolation](https://www.electronjs.org/docs/latest/tutorial/context-isolation)

## 主要取捨與風險

- 每資料夾隱藏檔利於搬移與復原，但首次掃描須讀許多小檔，且來源可能唯讀或被其他程式更動。SQLite 只能加速已索引資料，不能代替首次掃描或可攜檔的正確性。
- 專案根定義與每資料夾記錄分開，便於共用一個資料夾於多個專案；也需要規定只搬移子樹、專案根記錄遺失時的行為。
- 固定值型別讓查詢與 renderer 驗證容易；完全任意 JSON 彈性高，但型別轉換、排序和跨設備相容更難。建議先以少數明確型別驗證 POC。
- SQLite 是否採 WAL、FTS 或哪些索引，應由實際查詢與資料量決定；它們是後續優化手段，不是產品資料契約。

# Media Viewer 是什麼

**狀態：產品定位與已確認功能摘要；未定細節標明為待設計。** 來源是使用者於 2026-10-25 的多輪說明。[已核定方向](../DECISIONS.md) 與 [產品需求](../PRODUCT.md) 為細節依據。

注意：逐資料夾隱藏記錄已再確認；個別／一鍵清除、搬移後重新連結是必要能力，細節見 [儲存與清理](../STORAGE_OPTIONS.md)。

## 目的

Media Viewer 是一個本機優先的**媒體資料夾可視化與自訂檢視工具**。它讓使用者將一棵資料夾樹變成可搜尋、可分頁的清單，並為每個資料夾補充自己的名稱、數字、標籤和圖片，再自行決定資料如何排列與呈現。媒體分類包含遊戲、漫畫、影片、圖片相簿、音樂；外部公開中繼資料來源可依分類擴充。一般檔案管理器的固定清單／格狀畫面難以表達不同收藏或專案需要的資訊；此專案讓同一批資料夾在不同專案裡有不同解讀及顯示方式。

本產品重點是**檢視與描述資料夾**。開啟資料夾是 POC 的第一個內建動作；未來可以擴充其他控制電腦的動作，但它目前不是用來批次移動、刪除或重新整理使用者資料夾的檔案管理器。

未來可依分類進入不同的瀏覽視窗，例如漫畫／相簿閱讀及影片／音樂播放；使用者已要求暫緩這些畫面的細部設計。清除**本程式寫入的可攜資料**是明確要求，與刪除原始媒體資料夾不同。

## 核心概念

- **資料夾**：實際存在於檔案系統的單位；每個被納入範圍的資料夾有可攜的隱藏記錄及穩定 ID。
- **專案**：使用者選的根資料夾、媒體分類和檢視設定。可有巢狀專案，也可在同一根建立多個專案；資料夾搬入另一專案後套用目的版面，但原值仍可查看。
- **欄位值**：由資料夾自己的可攜記錄帶走的有型別內容。資料夾共用屬性是預設，確實需要不同值時才顯式建立專案私有覆寫；見 [資料夾與專案模型](../FOLDER_PROJECT_MODEL.md)。
- **cell／renderer**：cell 是畫面可排列的位置；renderer 決定對應欄位值如何顯示。資料本身與顯示方式分開。
- **可攜資料與索引**：專案設定、資料夾記錄及圖片隨資料夾移動；SQLite 是本機可重建索引，用於查找、組合條件與分頁。

## 使用者流程與功能

1. **建立專案**：指定根資料夾與遊戲、漫畫、影片、相簿、音樂或一般分類，選「顯示第 1 至 N 層」或「只顯示第 N 層」。根是第 1 層；分析先取得目錄結構、名稱與目前路徑。專案分類只影響檢視，不因掃描寫入每筆資料夾。
2. **檢視清單**：符合深度規則的資料夾按專案版面呈現；可設定每列及每頁資料夾筆數（例：2 筆／列、100 筆／頁），並以穩定順序切頁。
3. **設計畫面**：像積木一樣從左側拖組件進畫布，調整長寬、位置、文字和背景顏色，決定每個 cell 的欄位、renderer 及排列。POC 先驗證名稱、路徑等基本資訊與簡化文字 cell；MVP 再逐步增加其他顯示與操作，具體型別後議，見 [CELL_CATALOG.md](../CELL_CATALOG.md) 與 [EDITOR_DESIGN.md](../EDITOR_DESIGN.md)。
4. **編輯單筆資料**：對某個資料夾填寫自訂值。程式內保存成功後，清單立即反映新值；版面或列表設定變更也立即反映，無須重開。
5. **搜尋**：已選單一搜尋框加欄位提示；可按 key/value 組合條件，忘記 key 時直接輸入文字。任意一段文字相符都應可找到，查詢限當前專案掃描範圍，未放上版面的真實值也可搜尋。逗號與空格連接 AND，並支援引號、排除及單層 OR；特殊字元跳脫仍待設計。見 [SEARCH_DESIGN.md](../SEARCH_DESIGN.md)。
6. **攜帶與復原**：複製整樹或單獨搬移某資料夾到新設備，即使沒有原本本機資料庫，仍可讀回該資料夾的值與圖片；放入另一專案後用目的專案版面顯示，未配置的 key 留空或顯示預設，原值可於詳情檢視。第一版只驗證單向複製；複製出相同 ID 或不同版本時保留資料並提示。單獨帶走且尚未加入任何專案時的通用詳情排在 MVP。
7. **處理外部變動**：外部修改於視窗重新聚焦或按「重新掃描」時同步；不可寫資料夾可唯讀檢視，修改失敗必須說明原因。
8. **清理**：可清本專案於該資料夾的資料、該資料夾所有本程式資料，或盤點已連結範圍後一鍵清除；不刪原始媒體，離線與未連結副本要清楚報告。
9. **分類與來源**：來源網站可按分類擴充，取得候選後人工確認並保存到個別資料夾。漫畫／相簿閱讀和影片／音樂播放是後續方向，本輪暫緩細設計。

| 模式 | 展示方式 | 雙擊有效資料夾 |
| --- | --- | --- |
| CARD 多層 | 同頁平鋪 ROOT 與後代；層數可選全部或第 1 至 N 層，建立預設全部。 | 保留中央範圍，只更新右側內容。 |

### 記錄與邊界檢查

- 更新所在位置或右側內容前，先確認目標仍存在、有有效可讀記錄，且符合遊戲等既定邊界；遊戲 ROOT 本身有有效記錄時可正常展示。
- 尚未建立資料的資料夾拒絕進入，提示「此資料夾尚未建立資料」；受遊戲保護、不可納管的內部資料夾提示「此資料夾受遊戲邊界保護，無法建立資料」。拒絕時不改位置、歷史或右側，不在進入時自動建立隱藏資料。
- 損壞記錄另顯示復原原因，不能當成新資料夾自動覆寫。欄位缺值不等同沒有記錄，仍按既定缺值規則展示。
- 按需補掃只更新允許範圍內的讀取結果；建立缺失記錄仍經明確的掃描／建檔流程及既有確認。此條件優先於前輪「深入就補掃」的寬泛建議。

建立順序：**名稱 → 分類 → 選資料夾 → 群組 → 完成**。群組預設未分類，收藏獨立；完成前取消不建立可攜資料。完成後才建立並開始掃描，原有大量建檔與復原保護沿用。

| 區域 | 規則與責任 |
| --- | --- |
| 全域頂部列 | Logo、專案欄顯隱、搜尋範圍 SELECT／搜尋入口、Windows 視窗控制；前後導覽不放此處。空白區作視窗拖曳，輸入框／按鈕不能被拖曳區吞掉。 |

| 右側資料夾內容 | 目前資料夾屬性及漫畫／遊戲／相簿／影片內容；可調寬、關閉、工作區內放大。關閉面板不清資料。 |

工作區區塊放大與 Windows 最大化不同；閱讀器／圖片檢視是程式內覆蓋層，播放器全螢幕另有狀態。尺寸與捲動先存本機，專案版型可攜、個別閱讀偏好獨立；群組持久化格式留資料契約，不在此擅定為不可攜。

## 2. UI-R01：密度、尺寸與樣式代號（建議）

先使用一套標準密度與現有 Mantine 控制項，不新增另一套按鈕／表單方案。以下只供原型檢查，可調整，**不是從參考圖片採用的最終視覺尺寸**：

| 項目 | 初始建議值／行為 |
| --- | --- |
| 間距 | 基本級距 4／8／12／16／24／32px；同類控制項對齊，避免每頁自行設一套數值。 |
| 文字 | 主要文字 14px、輔助 12px、小標 16px、頁標 20px；先用系統字型，字重／品牌字體後議。 |
| 控制高度 | 一般輸入／按鈕 32px，工具列圖示互動範圍至少 28px；文字列高約 36px。 |
| 固定列 | 全域列 40px、專案列約 40px、狀態摘要約 24px；內容需要時可換行，不能遮住視窗控制。 |
| 左側欄 | 初始 240px、建議 200～360px；新增入口固定，群組標頭與項目區分開，展開群組內獨立捲動。大量群組仍需可抵達各標頭。 |
| 右內容區 | 初始約 380px、最小約 320px；中央區建議保留至少 360px。放不下時右區改覆蓋式面板，仍可關閉／放大，不硬擠成不可操作欄。 |
| 長內容 | 名稱／路徑可省略並提供完整提示或複製入口；編輯時可看全文。圖片等比，表格過寬在自己的區域捲動，不把整個應用撐寬。 |

配色只定語意代號：應用背景、面板背景、主要／次要文字、分隔、選取、焦點、警告、錯誤。**不指定色碼、明暗主題、圓角風格或陰影。** 使用者在 CELL 設定的顏色是內容樣式，不直接變成整個應用的主題。

原型檢查建議涵蓋 1280／1024／800px 寬度、長中文／日文名稱及不同 Windows 顯示縮放；這是後續驗收計畫，本輪沒有執行。

## 3. UI-R02：選取、導覽與「開啟」用語（建議）

- CARD／TREE 節點／TABLE 資料列單擊先選取，右區隨選取顯示；不因單擊就啟動 EXE 或打開檔案總管。
- TABLE 資料夾名稱雙擊或清單聚焦時 Enter 進入子層；點圖片縮圖直接進圖片檢視，符合 C-85。表單、搜尋、中文輸入法組字中不攔截 Enter／方向鍵。
- 專案工具列的「返回／前進」走該專案的瀏覽位置歷史；位置列／麵包屑提供返回父層。清單分頁明確叫「前一頁／後一頁」，不共用導覽狀態。
- 例如從 `/A` 切到 `/B/C`，返回歷史是 `/A`，父層是 `/B`；兩個動作不能都叫上一頁。這是本輪的具體化建議，不宣稱使用者已指定歷史算法。
- 「在程式內查看」「在檔案總管開啟」「啟動遊戲」分開命名。到達專案根／遊戲邊界時顯示原因，不為導覽自動向外掃描或向遊戲內寫記錄。
- TREE 只選取／縮放／平移，不拖動改父子關係；TABLE 列內編輯後加，先使用右區編輯。

## 4. UI-R03：自訂群組、最愛與最近新增（邊界案例建議）

已定：群組可自訂、愛心作用於專案、最近按新增且已歸組不列。為補「收藏是否也算歸組」的未細化情況，**本輪建議最近只列「沒有自訂分類且未收藏」的專案**：

| 情況 | 建議結果 |
| --- | --- |
| 新增 P，尚未分類／收藏 | P 出現在最近新增，按原新增時間排序。 |
| P 加入「動作遊戲」 | 最近不再列 P，從自訂群組開啟。 |
| P 按愛心 | P 出現在最愛；保留原自訂分類。若原本在最近，從最近移出。 |
| P 取消最愛，且沒有自訂分類 | 回到最近，沿用原新增時間，不假裝剛新增。 |
| 刪除自訂群組 | 專案轉未分類，收藏標記保留；按同一規則重新計算最近。原始資料不清理。 |

分類先以每專案一個自訂群組、收藏獨立標記作設計基線。移動提供拖放與選單；群組／專案的移除操作分開命名，不能讓側欄刪除變成清除可攜資料。上述派生細則待審，資料保存／匯出契約另交，不重問已定的最近新增語意。

## 5. UI-R04：搜尋與結果開啟（建議）

- 已定範圍 SELECT：有專案預設當前，未開預設全部已連結專案；未開時當前選項不可用。切範圍保留輸入文字，重新解析／查詢，不保留過時命中數。
- 跳窗列輸入、欄位提示、結果與範圍狀態；結果至少顯示名稱、路徑、來源專案與命中欄位。沒有結果、尚未索引、離線與查詢錯誤是不同狀態。
- 單擊結果先選取；Enter 或明確開啟動作才切至來源專案並定位資料夾，使用目的專案版面。保留查詢，方便返回結果，不在使用者打字時換專案。
- 全部模式的同名 key 提示型別／來源，歧義提供選欄位入口。重疊資料夾須可看來源專案；不同私有覆寫不可被靜默併掉。最終去重／結果契約另交，這份 UI 稿不代替索引設計。

## 6. UI-R05：共用控制、保存、焦點與提示（建議）

| 情況 | 共用行為 |
| --- | --- |
| 一般設定／編輯 | 明確「保存」「取消」；保存中防重複提交，成功後才顯示已保存並即時更新；失敗保留輸入及重試入口。 |
| 有草稿離開 | 提供保存、捨棄、繼續編輯；ESC／關閉面板不能靜默丟稿。不能成功保存時仍保留草稿。 |
| 開啟彈窗／覆蓋層 | 焦點進入該層，關閉回觸發控制；ESC 一次處理最上層，之後才是閱讀／播放全螢幕，再到工作區放大。 |
| 快捷鍵 | 已定閱讀鍵位沿用；新增建議 Ctrl+K 開搜尋、Ctrl+S 保存目前編輯。其他播放／編輯快捷鍵另列，不讓輸入中的單字觸發閱讀動作。 |
| 圖示與狀態 | 圖示有名稱及 Hover／聚焦 Tooltip；選取、停用、錯誤另有文字或標記，不只靠顏色。停用需能看出原因。 |
| 空／未知／不支援 | 說明當前範圍及下一步；缺值不造假、不寫回佔位。無法解碼的檔案保留項目及原因。 |
| 掃描／部分失敗 | 已完成、進行中、略過、失敗分開；取消後說明已完成部分，不能顯示成全部成功。 |
| 清理 | 預覽範圍與影響，再明確確認；結果列成功／失敗／未涵蓋。與側欄移除專案、刪群組分開。 |

表單錯誤顯示在對應欄位，執行失敗另有持續可查看的摘要；長時間工作保留進度／可取消狀態。不要為一般選取、看圖片或切模式增加確認窗。鍵盤可走到主要操作，中文組字時不送出搜尋；提示動畫及過場不是本輪視覺決定。

## 7. 媒體與共用狀態沿用規則

- 漫畫／相簿共用圖片載入、縮圖及檢視能力，版面分開。漫畫無圖片不顯示封面；遊戲缺大圖用佔位，不混成一種空值規則。
- GIF 只在可見範圍播放，閱讀／圖片檢視覆蓋層開啟時停背景；不加未核定的固定播放張數上限。
- 影片同時一個播放來源；離開內容區停止，記進度但由使用者選續播，不自動下一支。字幕拖到播放器後套至目前影片，載入失敗保留原字幕。
- 顯示資料、版型及受控動作分開；共用值與私有覆寫標清楚。瀏覽及版面調整不改原始媒體，缺值預設不成為真實資料。

本輪可按 UI-R01～UI-R05 審查，優先看尺寸／窄視窗、導覽區分、最愛與最近派生規則。其他已定方向不重問。通過後才將規則落成可重用元件與各畫面驗收；持久化、媒體引用與跨專案搜尋另交資料契約。

- 專案工作區左上方保留首頁／新增專案及更多操作的區域；更多選單的項目尚未指定。
- 圖示、顏色、圓角及邊界只是示意。區域分塊不要求最終有可見框線；線稿尺寸不是固定比例。
- 方塊按鈕代表在目前工作區內放大對應區塊，按 ESC 退出並還原工作區配置（C-74）；不另開獨立視窗。應用程式右上角的視窗最大化另有其用途。
- 左側專案欄、中央瀏覽區與右側資料檢視區需要能透過左右調整寬度；最小寬度、比例保存及窄視窗行為待議。
- 右區是所選資料夾的資料檢視位置；漫畫已依 C-75 開始 [內容與閱讀器設計](../MANGA_VIEWER_DESIGN.md)，尚未實作。其他媒體播放或遊戲操作仍按原分期討論，不能只因線稿保留位置就當成已實作。
- 「5000 筆」、頁碼、範例路徑及卡片數量都是示意，不建立新的數量上限、每頁設定或固定路徑格式。
- 底部錯誤資訊區是工作區的一部分；摘要、展開詳細內容及關閉方式待設計。

## 3. TREE 套件調查（官方資料）

以下於 2026-10-26 查閱，保留當時比較依據。使用者後續已核定 React Flow＋Dagre（C-74）；目前未安裝、未製作原型或量測本專案樹圖效能，實作前仍須確認穩定版本及目前 React／Electron 相容性。

| 候選 | 可直接沿用的能力 | 額外工作與取捨 |
| --- | --- | --- |
| **React Flow（`@xyflow/react`）＋Dagre：已選** | React 節點、縮放／平移、選取、縮放控制、適合視窗與 MiniMap；可選只渲染目前視窗可見的節點／連線。 | React Flow 本身沒有自動排版，需接一個 Dagre 排版轉換。可見範圍渲染也有成本，不保證大圖即順暢。 |
| react-d3-tree：未採用的調查參考 | 專為階層資料設計，內建 D3 樹形排版、縮放／平移、節點事件與自訂 SVG 節點；初版接線較少。 | 若之後需要額外導覽或大量節點渲染策略，需要另行補足；不能直接假定 SVG 全展開能滿足 10,000 筆。 |

來源：

- [React Flow 元件 API](https://reactflow.dev/api-reference/react-flow)：視窗與互動選項、可見範圍渲染。
- [React Flow 內建元件](https://reactflow.dev/learn/concepts/built-in-components)：MiniMap、Controls。
- [React Flow 排版說明](https://reactflow.dev/learn/layouting/layouting)：自動排版需外接引擎；Dagre 是官方列出的簡單樹形方案。
- [React Flow 效能建議](https://reactflow.dev/learn/advanced-use/performance)：大圖需控制節點複雜度與重新渲染，官方亦提出按需收合的策略。

## 4. TREE 的利弊與操作建議

| 優點 | 限制 |
| --- | --- |
| 容易看出父子關係、分支與資料夾所在位置。 | 分支寬或深時畫布很大；縮到整張圖可見，文字就會變小。 |
| 可以跨層探索，不必不斷進入／返回資料夾。 | 比較大量欄位、排序、批次編輯不如 TABLE 直接。 |
| 以選取和搜尋定位到目標，可保留路徑脈絡。 | 節點、連線、文字及原圖都會增加渲染負擔；套件不能保證任意數量不卡頓。 |

以下依 C-85 作已採互動與可調實作基線：

1. **分工**：CARD 看自訂內容，TREE 看結構，TABLE 比較欄位。三種模式共用同一批資料和一個右側資料檢視區，避免三套編輯／儲存邏輯。
2. **導覽**：滾輪縮放、拖曳空白處平移；提供適合視窗、回到所選節點及縮放按鈕。首次進入可適合視窗，之後不要在每次選取或改寬時重置使用者位置。
3. **節點簡化**：先顯示名稱及必要狀態，長名稱可看完整提示，完整欄位放右區；不把整張 CARD 的組件都搬進樹節點。
4. **全展開與效能**：已確認「全部」限於專案設定深度，不作無限層掃描；範圍內保留完整結構方向，先評估只渲染視窗可見元素。收合、只看某分支或效能模式屬額外建議，未經同意不改成預設只顯示少數層。
5. **安全與定位**：樹圖代表實際階層；平移、縮放和選取不改磁碟結構。建議停用拖曳改父節點及編輯連線。搜尋時可高亮命中並保留路徑，具體篩選規則另定。
6. **資料契約**：樹圖需要掃描結果提供父子關係。現有精確深度清單不能直接當完整樹；祖先結構資料應從目前掃描產生，不把舊絕對路徑寫入可攜記錄當身分。
7. **驗證**：後續原型用 1,000 筆代表樹及 10,000 筆壓力樹量測排版、首次渲染、縮放／平移與選取；現有名稱搜尋數字不能代替樹圖效能。

## 5. TABLE 與工作區的精簡方案建議

- TABLE 欄位範圍已確認為專案配置欄位（C-74）；不自動把所有發現的屬性展開成欄。名稱／路徑的預設配置及欄位操作細節待定；缺值維持空白。
- 基本表格沿用目前 Mantine 8 的 [Table](https://v8.mantine.dev/core/table/) 能力作基線；C-85 已採首輪基本排序／調寬、右側編輯，列內編輯後加。大量列與欄位配置的實體規格仍需驗證，不將基礎元件當完整資料表引擎。
- 區塊在工作區內放大，ESC 一次退出最上層並還原原配置；選單／跳窗優先於閱讀器／播放器全螢幕，再到工作區放大，不同時退出多層。尺寸／捲動先保存本機（C-85）。
- 模式切換共用專案、選取與查詢，各模式保留自己的頁碼／畫布位置；右區關閉不清資料夾值。窄視窗與具體還原時機交由原型驗證。
- C-85 已將上一頁／下一頁移至專案視圖工具列；TABLE／LIST 的子資料夾導覽不等同列表分頁，根邊界及搜尋結果切換的行為需寫成案例。

## 6. 決議後的規格與驗收工作

1. **TREE**：淡色祖先不算結果、不讓遊戲邊界變成可深入；搜尋高亮／定位與穩定父子資料需驗收，不能按分頁截斷結構。
2. **狀態與 ESC**：模式切換／面板調寬／跳窗重疊需有還原案例，使用本機保存及單層退出基線。
3. **TABLE**：定排序與欄寬有效範圍、缺值／型別不合、選列連動與逐層導覽；列內編輯留後續。
4. **無專案與搜尋**：模式按鈕先停用；搜尋依 C-85 可選全部專案，結果開啟與專案切換另有共同規格，不把全部結果直接拼成當前專案樹。
5. **側欄／首頁**：愛心作用於專案，最近按新增且排除已歸組項目；首頁採新增／最近／重連基線。視覺設計未定，細節見 [UI 外框](../UI_SHELL_DESIGN.md)。

| 看板／分欄 | 按父資料夾、標籤或狀態分組。 | 不是嚴格樹；分組數多時不易掃視。 |

## 概念模型

```text
資料夾 Folder（穩定身分、可攜記錄）
  └─ 共用有型別屬性（folderId / attributeId）與可選的專案私有覆寫
專案 Project（根資料夾、媒體分類、掃描模式、欄位映射、版面）
  └─ 掃描資料夾，renderer 依欄位映射顯示文字、圖片、標籤、動作等
```

方向：專案根目錄保存專案定義；每個資料夾保存其隱藏記錄，包含 folder ID、共用有型別屬性與必要時顯式建立的專案私有覆寫。圖片保存在可隨資料夾移動的位置，用相對引用連接。這是**概念圖而非正式 schema**；ID 格式、覆寫優先序及舊值遷移仍待設計。

例子：專案 A 可把別名 `tag` 映射到字串陣列屬性，專案 B 可把相同別名映射到不同的字串屬性；同名別名不代表同一屬性 ID 或型別。若兩個專案映射到相同的資料夾共用屬性，才讀到同一值；顯式私有覆寫另行標示。系統派生值（例如當前路徑）與使用者自訂值應有清楚區別，避免換設備後留下舊絕對路徑。

## 掃描與重疊專案

介面使用「顯示至第 N 層」及「只顯示第 N 層」。專案根資料夾標為第 1 層；實作內部可以從 0 計數，但對外語意要一致。專案 A 掃到巢狀專案 B 的根時，兩個專案可各用自己的版面讀取同一資料夾的共用值；專案私有覆寫須顯式建立，不以 B 的存在自動截斷 A 的清單。

需要測試的資料情境：搬移整棵樹、只搬移子資料夾、複製資料夾造成 ID 重複、資料夾記錄缺失或格式較舊、兩個設備分別修改後合併。衝突解決策略尚待決議。

# 資料夾內容與專案檢視的關係

整理日期：2026-10-25。**跨專案讀取及「資料夾共用屬性預設、專案私有覆寫須顯式建立」已核定；實體 schema 尚未定。** 此頁優先於早期文件中「所有值預設以 project ID 隔離」的模型。

## 已確認的搬移情境

```text
專案 1：/1，分類＝相簿             專案 2：/2，分類＝漫畫
        └─ A（帶有自己的隱藏記錄）  →  /2/A
```

掃描 `/2` 時，專案 2 直接列出 A，套用專案 2 的 cell 版面。A 記錄內原有的內容仍可於詳情查看。專案 2 若配置 `MANGA_NAME` 而 A 只有 `GAME_NAME`，前者顯示空白或設定的視覺預設；不得默默把 `GAME_NAME` 改名、轉型或刪除。若能明確判定 A 的內容類型與專案分類不符，顯示提示圖示但不阻止檢視。`/2/A` 如又搬到遊戲專案，同理重新套用目的版面。專案分類是檢視設定，**不能因掃描而寫進 A 的記錄**。

## 資料責任與待設計格式

| 位置 | 建議保存 | 不應自動保存 |
| --- | --- | --- |
| A 的可攜記錄 | folder ID、有型別的自訂屬性、來源網站 ID／URL 與擷取值、資產相對引用、必要的 schema 版本。 | 「目前位於漫畫專案」這類由所在路徑推導的專案分類。 |
| 專案根設定 | project ID、根與深度、媒體分類、欄位／查詢別名映射、cell 版面、列數／分頁、保存搜尋。 | 把 A 的原值複製成專案專用的第二份真相。 |
| 本機 SQLite | 掃描後的目前路徑、搜尋／排序索引、縮圖及狀態快取。 | 跨設備唯一權威資料。 |

**已核定的識別原則**：資料夾屬性有穩定身分與明確型別；專案 cell 用屬性 ID 或明確映射取值，不以同名 key 猜測型別。`game.name`、`manga.name` 是可考慮的語意命名空間範例，使用者看到的 `GAME_NAME`、`MANGA_NAME` 可當別名；確切 ID 與命名方式尚待 schema 設計。若同一資料夾需要在兩個專案有不同自訂名稱，須**顯式建立專案私有覆寫**，共用值仍保持原樣。

**不符提示的規則**：專案分類本身不會寫入 A，不能只因資料夾進入不同根就斷定 A 類型錯誤。只有資料夾明確記錄的內容類型或可信來源可支持不符提示；資訊不足顯示「未判定」。內容類型若由使用者手動標記，也不得由專案分類自動填入。

**搜尋的規則**：查詢範圍是目前專案掃到的資料夾；無 key 搜尋 A 的所有可搜尋真實文字／標籤值，即使某欄不在專案 2 版面上。欄位提示區分「本專案版面欄位」與「資料夾實際有的其他欄位」。視覺預設文字不是 A 的資料，不能被搜尋命中。

**缺值與不相容**：目的版面缺值只呈現空白或設定的視覺預設，不寫回 A；型別不合顯示警示及原值入口，不強制轉型。專案私有覆寫的優先序與清理、舊 JSON 值的遷移，仍待具體 schema 與驗收範例。

- 每個受管資料夾的記錄含穩定 folder ID、預設共用的有型別屬性、自訂及外部來源值，必要時另有顯式專案私有覆寫；圖片保存在其可攜資產區。見 [資料夾與專案模型](../FOLDER_PROJECT_MODEL.md)。實際檔名、版本與原子寫入仍待設計。專案根另保留專案定義／版面。
- 目前路徑是掃描結果與最後位置提示，不是 folder ID。啟動時先檢查已知根路徑，再掃已連結的根及子樹，以記錄中的 ID 更新路徑。移到已連結範圍之外時，由使用者選新根或該資料夾重新連結，不承諾自動掃描整台電腦。
- `/1/1` 與 `/1/2` 分別移至 `/1` 與 `/2` 時，兩份子資料夾記錄跟隨各自資料夾，重新連結後可個別檢視和清除。搬入專案 2 的掃描範圍即由專案 2 列出並套用其版面；移至任何已連結根以外，仍需由使用者指定新的掃描範圍。
- 同時發現兩個相同 folder ID 時可能是複製而非搬移；保留兩份與其資料並提示，不自動合併或覆寫。Windows 檔案系統 ID 只可作輔助訊號，不能作跨設備身分；其識別需結合磁碟區且可能隨操作改變。[Microsoft 檔案資訊文件](https://learn.microsoft.com/en-us/windows/desktop/api/fileapi/ns-fileapi-by_handle_file_information)
- 單獨搬移子資料夾時，其欄位值與圖片可攜；目的專案用自己的欄位映射與版面顯示，缺值留空或用視覺預設，原始欄位仍可在詳情查看。若尚未加入任何專案，通用資料檢視的規則見 O-56。

## 清理能力是這項方案的必要條件

1. 在資料夾詳情區分「清除此專案私有資料」與「清除此資料夾全部本程式資料」；前者只清顯式覆寫與關聯設定，沒有私有資料時可停用；共用的資料夾屬性不得因清除專案資料而誤刪。
2. 提供一個「清除所有本程式儲存資料」入口：先掃描**目前已連結且可存取的根及指定資料夾**，列出找到的記錄數、專案設定、圖片大小、本機 SQLite／設定與無法存取項目；使用者核對後一次執行，最後顯示成功、失敗及未涵蓋範圍。
3. 不可承諾清理尚未連結、離線磁碟或程式無法存取的副本。換設備時先重新連結或指定掃描範圍，仍可用同一清理流程。提供匯出備份及離線手動尋找方式。
4. 清理完成後，該專案／範圍要退出管理或停用寫入；否則下次掃描又會建立新記錄。若只清除單筆而專案仍在管理，需要 UI 明確提供「清除並停止記錄此項」或「清除後重新開始」的選擇。
5. 清理只能刪除能驗證屬於本程式的記錄、圖片與索引，不能依隱藏屬性或目錄名模糊刪除，更不能碰使用者原始媒體。唯讀與部分失敗要留下報告及重試路徑。

依 C-66（O-80 最新決定），單筆**徹底清除**後若搬入另一專案的掃描範圍，因已無可攜 ID 與值，按全新資料夾給新 ID、空白自訂值並套用目的專案預設顯示；不要求使用者判斷舊身分。原位置的停止記錄意圖只防止仍在原位時重掃立即重建，不能存入已清空的資料夾；重疊專案須共同遵守。[開發前審查包](../POC_PREDEV_REVIEW.md) R-03 建議把相對位置排除寫入目前所有涵蓋專案的可攜設定，根離線時不過期，仍待使用者審核。

**尚待細化**：資料損壞保留原檔、同名目錄驗證歸屬、舊 project-scoped 值明確遷移的原則已依 C-57、C-59 核定；覆寫優先序、實體 schema 與失敗範例仍待 O-76、O-77。尚未加入任何專案時的通用詳情已排在 MVP；清除後預設停止記錄，排除機制與重疊專案案例仍待具體設計。

# 積木式 Cell 編輯器

**狀態：格線、樣式、預設版面、真實預覽、編輯復原與碰撞原則已確認；尺寸等細節待設計。** 使用者希望在 `src/app/editor/` 的概念基礎上，從左側選組件拖入編輯畫布，像積木一樣組裝一筆資料夾的顯示模板；可調整每個 cell 的長寬、文字及背景顏色等。此編輯器是產品核心功能，現有程式碼不足以當最終設計範本。

## 一個專案的編輯流程

```text
左側：組件／欄位清單  →  中央：單筆資料夾模板畫布  →  右側：選中組件的設定
                          ↓ 預覽實際資料夾
                      儲存專案版面 → 清單立即套用
```

左側分為資料欄位（系統名稱、路徑與自訂文字／數字／標籤／日期／圖片）、純視覺元件（例如文字標籤、分隔線）及動作（先有開啟資料夾）。拖入後建立**組件實例**，而非複製某個資料夾的值。中央畫布編輯的是專案的單筆資料夾模板；清單對每個符合條件的資料夾套用同一版面，填入各自的值。資料夾搬入另一專案後沿用自己的原值，由目的版面決定顯示；缺 key 留空或用視覺預設。單筆資料編輯畫面只改值，不改整個專案版面。POC／MVP 元件切線見 [CELL 目錄](../CELL_CATALOG.md)。

右側設定依組件類型提供資料來源、字體與背景顏色、字體大小、對齊、內距、邊框、圖片裁切等適用項目。畫布上可拖動、調整寬高、選取、刪除與預覽；未保存變更要有取消或還原路徑。設定的可攜資料應是版本化的版面模型（組件 ID、類型、綁定的 field ID、格線位置／大小、樣式和動作設定），不直接儲存 React 元件或第三方函式庫物件。

## `react-grid-layout` 的定位

目前專案已使用 `react-grid-layout`。其官方文件列有外部拖入、可調整尺寸、序列化版面、響應式布局等能力，符合積木式畫布的核心操作；**建議先保留它作為拖放與格線佈局引擎**，在 React + Vite 遷移後用實際編輯情境驗證。組件目錄、屬性面板、資料綁定、儲存格式、取消／還原和預覽仍需由產品自己的模型處理。[react-grid-layout 官方文件](https://github.com/react-grid-layout/react-grid-layout)

此建議不把現有 `editArea.tsx` 的 20 欄、固定 1000px 畫布或目前的表單接線當成正式規格。Vite 遷移與函式庫版本差異須獨立驗證。

## 必須先說清楚的互動規則

1. **格線與卡片尺寸（已核定）**：使用固定邏輯格線與最小可讀寬度；視窗變窄時換行或減少每列筆數，不裁切內容。實際尺寸仍需量測。
2. **碰撞與重疊（已核定）**：兩個組件拖到同一格時預設自動推開；無可用空間則拒絕並提示，不允許超出畫布。有意疊圖需日後另設圖層功能。
3. **樣式自由度（方向已核定，分期待定）**：目標支援文字／背景色、字級、粗細、對齊、內距、邊框、圖片裁切與自訂色碼；POC 只驗證基本樣式，其他逐步加入。任意 CSS 或腳本後議。
4. **預設版面（已核定）**：新專案先有可用版面，再由使用者自訂。POC 每專案一份模板；同專案多版面及單筆覆寫是後續候選，不列入 POC。
5. **預覽內容（已核定）**：使用真實資料夾的名稱、目前路徑等資料預覽；空值顯示佔位，不寫入假資料。預設選哪一筆仍待設計。
6. **編輯歷程（已核定）**：提供未保存提示、取消、多步復原與重做；具體歷史深度與分組待設計。
7. **可用性（已核定）**：屬性面板可用數值輸入位置與尺寸；鍵盤快捷鍵後議。

## 驗收情境草案

POC 從左側拖入系統名稱、目前路徑、基本文字值及「開啟資料夾」；調整位置與尺寸、基本文字和背景色，選兩個實際資料夾預覽，確認它們共享版面但值不同。儲存後返回列表，所有項目立即套用；取消未保存編輯不改變既有列表。縮放視窗及每列 2 筆時，內容不被重疊或裁掉。標籤、圖片及更多樣式的編輯演練屬後續候選；細部格線待 O-83。

# 搜尋功能設計選項

> 2026-10-27：C-87 已授權並完成首輪第二／三階段；當前契約、實測及未涵蓋範圍以 [STAGES_2_3.md](../STAGES_2_3.md) 為準。下文保留前輪設計與當時狀態，舊「未實作／待 schema」不代表目前現況；視覺風格仍未定案。

**狀態：方案 A、完整搜尋的基本語法、單層 OR 與效能測試目標已核定；完整語法排在 POC 基本名稱／路徑搜尋之後，實際效能仍待量測。** 使用者希望按專案欄位 key 與值組合查詢，例如 `name:chinese,pic tag:2025,game date:20251012`；忘記 key 時也能搜尋，任意一段文字相符都應可找到。搜尋結果須在程式內修改欄位值後立即更新。使用者熟悉 E-Hentai 查詢習慣，但尚未要求逐字相容。

**C-85 範圍更新（O-92）**：搜尋欄提供 SELECT「當前專案／全部專案」，有開專案時預設當前，未開專案時預設全部。全部指已連結專案；第一階段已實作名稱／路徑範圍搜尋、跳窗與來源開啟（最多顯示前 50 筆，僅已掃描資料）。以下完整 key/value 尚未實作，列第二階段；原「本專案」描述是當前模式，全部模式的欄位消歧、覆寫值與去重由 Agent 細化，不能將同字串 key 合併。

全部模式的設計基線：結果標示所屬專案／路徑；同一 folder ID 被重疊專案收錄時保留來源關係，顯式私有覆寫不同時不可靜默併掉值。遇重複 ID 衝突仍走原問題流程。離線／未索引範圍顯示不完整；跨專案 `key:value` 必須明確標示解析後的穩定欄位與專案，無法消歧就要求選欄位，不猜測型別。具體 AST／結果格式待規格審查。

## 方案 A：單一搜尋框 + 欄位提示 + 自由文字（已選）

- 輸入 `key:value` 時顯示本專案映射的欄位及掃到的資料夾實際擁有的其他可搜尋欄位，標明各自名稱、型別與來源；可點選產生條件，別名衝突需提示。
- 不輸入 key 的文字會搜尋本專案掃描範圍內資料夾真正保存的名稱、路徑、文字、標籤等可搜尋值，即使沒有放在目前版面上；結果標示命中的欄位。忘記 key 時仍可直接搜尋，也可展開欄位清單。
- 查詢先解析成有型別的條件，再交給 Electron main 驗證與查詢 SQLite；renderer 不直接傳入 SQL 或未驗證的欄位名稱。
- **已核定的基本語法**：保留 `key:value`、以空格組合 AND、引號包住含空格的值及無 key 搜尋。`name:chinese,pic` 表示同一 name 同時含兩段文字，等價於 `name:chinese name:pic`；`tag:2025,game` 表示兩個標籤都符合。`-` 排除緊接條件，`~` 連接單層 OR 群組，群組內是 AND。特殊字元跳脫仍待設計。這是本產品的自訂規則，不能宣稱與 E-Hentai 完全相容。
- 共用屬性以固定屬性 ID 查詢；輸入框中的 key 是該專案不分大小寫且唯一的查詢別名，其他發現的欄位需要明確消歧。顯示名稱可重複或改名，不能讓 `NAME`、`name` 的解析依賴猜測。這項原則已核定，實際別名映射格式待設計。

**選用原因**：直接支援使用者提出的輸入方式，也提供忘記 key 時的退路。可先實作有限語法，再依使用情況增加運算子。逗號、空格、基本優先序與錯誤提示原則已定；跳脫與實例仍需驗收。

## 方案 B：視覺條件建立器 + 一般搜尋框（第一輪未選）

- 一般搜尋框查所有可搜尋文字；精確條件由「選欄位 → 選運算子 → 輸入值」的表單組成，可新增 AND／OR 條件。
- UI 把查詢結構送給 main process，不必讓使用者學會文字語法；型別錯誤可以直接在欄位旁提示。

**優點**：條件清楚，日期、數字比較與多層括號較易呈現。**缺點**：對已知道查詢語法的使用者步驟較多，且無法直接貼上示例查詢；首輪 UI 較重。可留作進階查詢畫面，不必取代方案 A。

## 與 E-Hentai 習慣的關係

EHWiki 的搜尋說明使用 `namespace:value`、空格分開條件、引號包詞組、`-` 排除及 `~` 表示 OR；它明示**逗號會被忽略**。本產品建議保留熟悉的外形，並提供「逗號後的值仍屬同一 key」的便利縮寫。這是刻意自訂的行為：搜尋框需顯示解析後條件，讓使用者看出是 AND 或 OR。[EHWiki 搜尋操作說明](https://ehwiki.org/wiki/Gallery_Searching)

## 共同的索引方向

可攜資料夾記錄仍是權威資料。SQLite 可按專案掃描範圍、folder ID、共用屬性 ID、可選的顯式私有覆寫及已驗證值型別建立可重建索引；不能把 project ID 當成所有值的預設身分。文字查詢考慮 FTS5，標籤與日期／數字使用符合型別的索引或查詢表。使用者已要求**任意子字串**匹配；FTS5 的 trigram 有助於三個以上 Unicode 字元的子字串，但官方說明短於三字的全文查詢不能直接匹配，某些 `LIKE` 查詢會退化成線性掃描。大量資料下，1–2 字元搜尋需要額外索引或明確效能策略，不能宣稱現有 FTS 設定已足夠。[FTS5 官方文件](https://www.sqlite.org/fts5.html)

索引與可攜記錄不一致時，以可攜記錄重建；修改成功後立即更新當前畫面和搜尋結果。結果在同一條查詢中採穩定排序與分頁，避免切頁重複或漏項。POC 先以約 1,000 筆資料夾驗證，這是基準而非硬上限；短於三字的搜尋可先驗證縮小範圍後掃描，再視量測增加額外索引。首次讀取每資料夾記錄與已建索引後的查詢須分別量測。

**跨專案搬移的規則**：目的專案掃到資料夾後，資料夾原有文字／標籤即使未在目的版面上，也可在詳情查看。無 key 搜尋涵蓋目前專案掃描範圍內所有資料夾真正保存的可搜尋文字／標籤；欄位提示區分本專案映射與實際發現的其他 key。視覺預設不當作真實可搜尋值。POC 先做基本名稱／路徑搜尋；完整 key/value 語法在後續階段交付，效能樣本待 O-78。

## 待審核

1. 完整 key/value 搜尋首版的單層 OR 群組、群組內 AND、`-` 排除緊接條件及錯誤顯示原則已核定；特殊字元跳脫與實際範例仍待設計。這不是 POC 名稱／路徑搜尋的前置條件。
2. 查詢別名不分大小寫且專案內唯一已核定；欄位改名後是否保留舊別名、已保存查詢如何更新，仍需設計。
3. 無 key 搜尋目前專案的名稱、路徑、文字和標籤已核定；數字／日期無 key 查詢的格式與是否搜尋尚待設計。
4. 任意子字串匹配已核定；中文、英文、1–2 字元及大量資料的效能目標與索引策略仍待量測。
5. 排除詞與 OR 已選為基本語法；數字大小比較、日期範圍及保存查詢的具體交付工作仍待排定。跨專案範圍已由 C-85 確認，消歧／去重尚待規格及驗收。`date:20251012` 與 `date:2025-10-12` 已核定為同一天的精確查詢。

| STRING／文字 | 自訂名稱、簡介、備註、來源連結 | 可為使用者填寫或來源匯入；換行、空值和長字串需有顯示規則。 |
| NUMBER | 評分、集數、時長、檔案大小、遊戲時數 | 數值與單位分開；如檔案大小與時長屬計算值，需標示來源及更新時間。 |
| DATETIME／DATE | 發行日、加入日、上次整理日、檔案修改時間 | 明確區分來源日期及系統時間；發行日可能只有年或年月，不能硬補日。 |
| BOOLEAN／狀態 | 已讀、已玩、已完成、稍後看 | 可用圖示、文字或徽章；未填不等於 false。 |
| 標籤／選項 | 類型、語言、平台、自訂標籤 | 多值與單值不同；來源標籤與手填標籤可並存。 |
| 圖片／封面 | 自訂圖、來源封面、資料夾中選定的圖片 | 原圖可攜、縮圖本機快取；畫面避免一次載入大量原圖。 |
| 衍生資訊 | 檔案數、子資料夾數、媒體數、容量 | 可能需要額外掃描；先顯示計算中／上次計算，不阻塞基本列表。 |
| 來源／連結 | 商品頁、畫廊頁、匯入來源、上次同步時間 | 提供可追溯性；不是所有外部來源都有相同欄位。 |

# 從外部來源補充遊戲與漫畫資料

整理日期：2026-10-25。**狀態：分類與外部公開資料的可擴充方向已核定；網站來源、欄位映射與里程碑待定。** 媒體分類包含遊戲、漫畫、影片、圖片相簿、音樂；初始仍以資料夾為掃描單位。外部來源提供候選值，不替使用者決定作品身分，確認後寫入對應資料夾的可攜記錄。

## 通用模型

- 媒體分類屬於專案設定，不會因掃描或搬入目的專案而寫入資料夾。分類可提供常見欄位建議與適用來源 adapter，但不限制使用者自訂欄位；只有資料夾本身明確保存內容類型或有可信來源時才顯示不符提示，否則標示「未判定」。
- `SourceRecord` 保存來源類型、網站、來源 ID／URL、擷取時間及原始欄位；`FieldValue` 是本專案實際採用的值，並記錄人工或匯入來源。不同網站可對映同一語意欄位，但不直接覆寫。
- 外部資料、圖片與來源紀錄隨個別資料夾搬移。來源以 adapter 擴充；首個網站在進入該階段時再選。遊戲與 E-Hentai 以下僅是可行性範例，不代表它們已排入 POC。
- 漫畫、遊戲、相簿及影片已進入專屬內容設計，均未實作，不成為原 POC 前置條件。C-85 採來源先一個、以 URL／ID 取得候選後確認，首個網站到該階段再選；音樂明確延至下一版。

## 共通操作

`選取資料夾 → 貼商品／畫廊連結或辨識本地線索 → 取得候選 → 預覽標題、日期、圖片、標籤及來源 → 確認欄位映射 → 填空值或逐欄覆寫 → 即時更新列表`

- 每個來源做獨立 adapter，保留來源 URL／ID、擷取時間與原始欄位語意。使用者的自訂值與匯入值要能區分；再次抓取預設只填空值，不靜默覆寫手填資料。
- 批次處理要能暫停、顯示成功／模糊／失敗筆數，模糊匹配先進審核佇列。資料夾名稱只能當候選提示，不能當確定來源。
- 圖片若要可攜保存，需對各來源確認可使用的方式與條款；圖片網址不可直接當作跨設備必然可用的資產。敏感憑證不寫入專案根或可攜檔。

## 遊戲

先用商店商品 URL／商品 ID 取得精確候選，再允許用資料夾名稱搜尋並手動選。需區分遊戲**首次發行日期**、特定平台／版本發行日期與使用者**購買日期**，避免把不同概念填入同一 date 欄。IGDB 官方 API 提供名稱、封面、首次發行日期及對其他商店的 external game ID；其 Twitch 註冊使用 confidential client secret，若作為內建來源，桌面端憑證與部署方式須另設計，不能把共用 secret 放進應用程式。[IGDB API 文件](https://api-docs.igdb.com/)

Steam 官方 `IStoreService/GetAppList` 可列出商店 app 與 ID，但它不是「給一個資料夾就得到全部作品資訊」的保證；其他商店要逐一驗證 API、授權及可取得欄位。[Steamworks IStoreService](https://partner.steamgames.com/doc/webapi/IStoreService)

**快速完成百筆的建議**：先匯入已知商店連結／ID 的清單，批次取得候選；未有 ID 者以名稱產生候選供人工快速確認。可支援使用者提供 CSV 對照，但不能假設所有商店都提供同一種匯出格式。是否先支援 Steam、IGDB 或其他商店，見 O-50。

## E-Hentai 畫廊

E-Hentai 的 `gdata` API 需要畫廊 `gid` 與 token，畫廊 URL 自帶兩者；回應範例含標題、日文標題、縮圖 URL、分類、上傳時間、頁數及標籤。API 文件說明每次最多 25 筆，批次需控制速率。[EHWiki API](https://ehwiki.org/wiki/API)

第一輪建議支援貼畫廊 URL，並在下載資料夾內有來源連結或 `galleryinfo.txt` 時嘗試擷取；後者是否存在取決於下載方式，不能假設每個資料夾都有。[EHWiki 下載說明](https://ehwiki.org/wiki/downloading) 無連結時只提出可能候選，讓使用者確認；保留原語言標題與目前自訂名稱。`posted` 是畫廊上傳時間，不應自動當作作品發行日期。圖片保存方式及憑證需求再依實作來源確認。
