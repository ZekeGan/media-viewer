## POC 的驗證目的與範圍

POC 要回答四個問題：① 能否按兩種深度規則把資料夾變成穩定清單；② 使用者能否像組積木一樣建立**一份專案 CELL 模板**，對不同資料夾顯示各自真實值；③ 資料夾與整個專案搬移或換設備後，值、圖片及適用的版面能否復原；④ 寫入失敗與清理時能否明確知道哪些資料保留、哪些成功處理。若只做到掃描或靜態卡片，POC 不算通過。

| POC 必做 | 不放進 POC，依已核定方向後續處理 |
| --- | --- |
| Windows 桌面版；React + Vite renderer、Electron IPC；先保留 Mantine。 | macOS 驗收、完整視覺風格、任意系統命令。 |
| 建立／切換專案、選媒體分類、兩種深度模式；掃描進度與可恢復錯誤。 | 媒體分類專屬閱讀／播放、網站中繼資料匯入。 |
| 平面清單、真實名稱與路徑、開啟資料夾；每列／每頁設定、穩定分頁與名稱／路徑子字串搜尋。 | 樹與蜂巢視圖、完整 key/value 查詢、批次編輯與保存搜尋。 |
| 每專案一份可編輯的 CELL 模板；名稱、路徑、自訂文字及開啟按鈕；拖入、綁定、移動、縮放、基本顏色、真實預覽、保存／取消與復原／重做。 | 單筆版面覆寫、NUMBER、DATETIME、標籤與圖片 CELL 等候選組件，進 MVP 時再選順序。 |
| 單筆文字值與圖片原檔可攜保存；資料夾／根搬移、跨專案讀值、空值呈現、重新連結；個別與一鍵清理。 | 沒有原專案的單獨資料夾通用詳情、雙向設備自動合併。 |

上述為**功能邊界**。UI 細節見 [線框](POC_WIREFRAMES.md)，資料契約與失敗邊界見本書第 2–4 節及 [POC 技術架構](POC_TECH_ARCHITECTURE.md)；O-80 搬移後當作新資料夾已核定，實體 schema 還需審核。

## 1. POC 要展示什麼

使用兩個受控測試根並各建一個專案，包含 `P1/A`、`P1/B/C` 與 `P2`；另外在 `P1/B` 建巢狀專案、在 `P1` 建第二個同根專案作重疊測試。不要操作使用者實際媒體。根是第 1 層，`A`／`B` 是第 2 層，`C` 是第 3 層。

| 步驟 | 使用者操作與預期畫面 | 驗證點 |
| --- | --- | --- |
| 1 | 選 `P1` 建專案、選媒體分類與深度；「顯示第 1 至 2 層」列出 `P1`、`A`、`B`，「只顯示第 3 層」只列 `C`。 | 已走訪的祖先也有可攜記錄；不掃超過設定深度，資料目錄不出現在列表。 |
| 2 | 預設卡片立即顯示真實資料夾名稱、目前路徑及「開啟資料夾」；設每列 2 筆、每頁 100 筆。 | 設定保存後畫面立即更新，重新啟動仍一致；按鈕只開啟該資料夾。 |
| 3 | 在側欄替 `A` 保存一個自訂文字值，並附加一張測試圖片；從左側拖入名稱、路徑、文字與開啟按鈕，調位置、尺寸及基本顏色，以真實 `A`、`B` 預覽。 | 所有項目共用專案模板，但值各自不同；保存後清單即時更新，取消不寫入。圖片原檔可攜，不要求 POC 卡片有圖片 CELL。 |
| 4 | 手動在測試資料樹把 `A` 搬到 `P2/A`，在程式中掃描或重新連結；另測整個 `P1` 根改路徑。 | 依 folder ID 讀回 `A` 的值與資產；由目的專案版面顯示，目的版面沒有的 key 留空，原值仍可在詳情檢視。根一起搬移時專案版面可復原。 |
| 5 | 模擬新設備：複製測試樹到不同路徑，使用空白本機資料重新連結。 | 不依賴舊絕對路徑或 SQLite，可讀回 folder ID、文字值、原圖及隨根搬移的專案設定。圖片 CELL 不要求列為 POC 首批組件。 |
| 6 | 預覽後個別清除 `A` 的本程式資料，重新掃描；再對另一受控根演練一鍵清理。 | 不刪原始媒體；同位置重掃不自動重建已停用的記錄；顯示成功、失敗和未涵蓋範圍。 |

### POC 核心驗證：自定義 CELL

POC 的目的之一，是證明**一份專案卡片模板可以讓使用者自由編排，又能對每個資料夾顯示不同的真實值**。資料夾值保存在自身記錄；CELL 的組件類型、欄位綁定、位置、尺寸與樣式保存在專案設定。調整版面不得改動資料夾值；編輯 `A` 的值不得改動 `B` 的值或版面。

| 編輯器區域 | POC 必須能做的事 |
| --- | --- |
| 左側組件清單 | 選擇資料夾名稱、目前路徑、自訂文字，以及「開啟資料夾」按鈕，拖入畫布。 |
| 中央卡片畫布 | 移動組件、調整寬高；碰撞時推開，無空間時拒絕並提示；不能拖出畫布。 |
| 右側設定 | 替文字組件選擇穩定屬性 ID；設定基本文字與背景顏色。按鈕只可選已允許的「開啟目前資料夾」動作。 |
| 真實資料預覽 | 切換 `A` 與 `B`：相同排列、不同名稱／路徑／自訂值；`B` 缺少自訂文字時只顯示空白或編輯佔位，不寫入假值。 |
| 完成操作 | 未保存提示、取消與基本復原／重做；保存後列表所有卡片立即套用，重開仍一致。 |

**通過條件**：使用者不用改程式碼就能組出「名稱＋路徑＋自訂文字＋開啟按鈕」卡片；改 `A` 的文字只更新 `A`，改模板位置則更新目前專案的所有卡片；把 `A` 搬到 `P2` 後，值仍可讀，但顯示方式由 `P2` 模板決定。圖片原檔的可攜性要驗證，圖片 CELL、NUMBER、DATETIME 等新增組件留到 MVP 挑選。詳細互動原則見 [編輯器設計](EDITOR_DESIGN.md)。

POC 編輯器以「一個專案、一份卡片模板」為準。拖入建立**組件實例**，不能複製預覽資料夾的值；系統名稱／路徑來自當前掃描，自訂文字綁定穩定屬性 ID。預設卡片在使用者尚未編輯時也必須能用。碰撞推開、無空間拒絕、未保存提示及復原／重做為已核定互動；格線數值、歷史深度與樣式參數仍由 O-83 的設計樣本決定。

POC 搜尋先驗證目前專案的名稱／路徑子字串、穩定排序與分頁。完整 key/value 語法、批次編輯、保存搜尋、其他資料型別、樹與蜂巢視圖、網站匯入和閱讀／播放依已核定分期後續加入。第一版以 Windows 驗收，React + Vite 遷移時保留 Mantine；樣式風格尚未定。

## 2. 資料放哪裡：建議的最小契約

建議每個受管資料夾有 `.media-viewer/` 隱藏資料目錄（具體審核見[開發前審查包](POC_PREDEV_REVIEW.md)），其中 `folder.json` 是該資料夾的權威記錄，`assets/` 放複製進來的圖片原檔。專案根同一資料目錄下另有 `projects/<projectId>.json`；同根多專案各用獨立 ID／檔案。Windows 設 Hidden 屬性，app 掃描、搜尋與普通列表永遠排除自己的資料目錄。遇到同名但無合法歸屬標記的目錄，不接管、不覆寫、不清理。

`folder.json` 的**示意**，不是最終 schema：

```json
{
  "kind": "media-viewer.folder",
  "schemaVersion": 1,
  "folderId": "folder-a-stable-id",
  "revision": 3,
  "attributes": [
    {
      "attributeId": "shared-title-id",
      "key": "CUSTOM_NAME",
      "type": "string",
      "value": "作品 A",
      "source": "manual"
    }
  ],
  "projectOverrides": {},
  "assets": [{ "assetId": "cover-id", "relativePath": "assets/cover-id.png", "originalName": "cover.png", "mediaType": "image/png" }]
}
```

專案設定保存 `projectId`、根 folder ID、媒體分類、深度模式、欄位 ID／查詢別名映射、單筆 CELL 模板與列／頁設定；保存搜尋在 MVP 放此處。資料夾記錄只保存自己的有型別值、圖片與必要來源，不因移入某專案就寫入該專案分類。**路徑是掃描結果，不是身分**；跨設備路徑只在本機索引重算。

同根多專案各自的 `projects/<projectId>.json` 可採以下**示意**；CELL 的細部樣式仍待 O-83：

```json
{
  "kind": "media-viewer.project",
  "schemaVersion": 1,
  "projectId": "project-1-stable-id",
  "rootFolderId": "root-1-stable-id",
  "revision": 1,
  "name": "漫畫專案",
  "mediaCategory": "manga",
  "depth": { "mode": "through", "level": 2 },
  "fieldBindings": [{ "alias": "title", "attributeId": "shared-title-id", "type": "string" }],
  "cells": [{ "cellId": "cell-title-id", "kind": "field-text", "attributeId": "shared-title-id", "grid": { "x": 0, "y": 0, "w": 12, "h": 1 }, "style": { "textColor": "#111111", "backgroundColor": "#ffffff" } }],
  "list": { "itemsPerRow": 2, "pageSize": 100 },
  "excludedRelativePaths": []
}
```

同一 `CUSTOM_NAME` 文字可以在不同專案指向不同 `attributeId` 與型別；不能靠 key 名稱合併。CELL 引用系統欄位或穩定屬性 ID，缺值是空白／視覺預設，不寫回也不作搜尋值。顯式專案私有覆寫可用 `projectId + attributeId` 表示並保留共用原值；POC 演練只需共用文字值，但可攜格式範例應覆蓋覆寫與同根雙專案。舊本機 JSON 的轉換映射需另附一組「轉換前／後」範例，先備份，不能在啟動時默默改寫資料夾。

本機 SQLite 若導入，只保存可重建的目前路徑、專案掃描範圍、排序／搜尋索引與縮圖快取；不得成為唯一資料來源。POC 基本流程不以選定 SQLite 驅動為前提。

## 3. 保存、搬移與清理：建議流程

1. Electron main 負責掃描與寫入，preload 暴露受控 IPC；renderer 只傳已驗證的專案／資料夾 ID、文字值、模板及設定，不直接決定任意檔案路徑。
2. 保存前讀目前 `revision` 並驗證型別、資料目錄歸屬與可寫狀態；修訂衝突先停止，保留雙方內容供比較。寫入採「同目錄暫存檔 → 驗證 → 保留上一版 → 替換」的候選流程，Windows 上的中斷／替換行為需以受控資料樹實測後定稿。
3. 可攜檔保存成功才更新畫面與本機索引；索引更新失敗則標「待重建」，下次從可攜檔修復。失敗時不把未保存的畫面值顯示為已完成。
4. 啟動先核對已知根；根不存在時顯示「待重新連結」，讓使用者選新位置。掃描新根依記錄 ID 對回；搬入另一專案範圍則套目的版面，不轉寫原值。
5. 同時找到兩個相同 folder ID 時，兩者暫停寫入。使用者選「搬移後重連」或「這是副本」；副本先保留值再分配新 ID，不靜默合併。
6. 清理先預覽可驗證屬於本程式的記錄、資產、專案設定與本機索引；只清已連結且可存取範圍，逐項報告結果。個別清除預設停止記錄此項；全部清除後退出對應管理範圍。原始媒體不可刪除。

**O-80 已核定的界線**：單筆資料夾內的全部程式資料徹底刪除後，原位置重新掃描仍停止記錄；若搬到另一專案的掃描範圍，視為全新資料夾，給新 folder ID、空白自訂值和目的專案的預設顯示，不沿用被刪資料，也不要求辨識舊身分。停止記錄意圖不得殘留在已清理的資料夾；[開發前審查包](POC_PREDEV_REVIEW.md) 建議放在現有涵蓋專案的可攜設定中，重疊專案與過期案例須依該表審核。

## 4. 出錯時怎麼恢復

| 情境 | 建議結果與下一步 |
| --- | --- |
| 無權限、唯讀、離線根 | 其他項目繼續掃描；列表保留狀態，顯示原因，允許重新連結或重試；不偷偷改存本機。 |
| 記錄損壞／格式過新 | 保留原檔，停止該筆寫入；可查看錯誤並用可用備份恢復。不能把 SQLite 快取當成原值覆寫它。 |
| 寫入中斷／索引落後 | 從上一個有效可攜檔恢復或重試；索引可重建，不要求使用者手動修資料庫。 |
| 外部同時修改／修訂不符 | 不採最後寫入者勝出；保留兩份內容，顯示差異與重新套用入口。 |
| 重複 folder ID | 兩份都列出但暫停寫入，等待「搬移」或「副本」判定。 |
| 同名非本程式目錄 | 不接管、不刪除；指出阻擋位置，請使用者處理後重試。 |
| 批次或一鍵清理部分失敗 | 列出已成功、失敗、離線／未連結項目；重試僅針對失敗項，避免再次刪已清項。 |

POC 的錯誤呈現建議先用列表狀態、側欄說明及一個集中「問題／復原」入口；具體視覺稿後議。`junction`／符號連結預設不跟隨，避免循環與重複資料。

## 5. 建議驗收與交付門檻

- **必要情境**：上表 1–6 的一條正常閉環，加上唯讀、重複 ID、損壞／中斷寫入及部分清理失敗的受控案例。每項記錄輸入、預期、實際結果；只對具體風險增加測試，不重複全量測試。
- **資料量**：以 1,000 個資料夾作代表性樣本；首次掃描與名稱／路徑搜尋分開量測。10,000 筆作壓力情境；索引後暖機搜尋 200ms 是工程目標，固定設備、查詢、次數及統計方式後才判定是否達成。未執行時不得宣稱達標。
- **可攜性**：複製整根可還原專案設定與每筆值；單獨搬移子資料夾可讀值及圖片，但原專案版面若未隨根搬移，不保證復原。SQLite 刪除後仍可由可攜檔重建。
- **進入程式實作前**：核對本設計包的示意 schema、O-80 原位置排除的過期／重疊案例、舊 JSON 對照樣本、清理範圍及 UI 最小流程。進入 MVP 前才選首批型別、來源網站與閱讀／播放細節。

## 6. 審核後仍需定稿的設計

1. **資料格式**：本書 `.media-viewer/`、`folder.json`、專案 JSON 與覆寫欄位只是示意。需審核實際檔名、歸屬標記、版本與一份舊 JSON 轉換前後樣本（O-76）。
2. **單筆徹底清理後搬移**：新位置視為新資料夾已核定；仍需定稿原位置排除何時過期、重疊專案是否都停止記錄，以及暫時離線時不誤判搬移的案例。
3. **Windows 寫入／復原**：暫存、備份、替換及中斷時保留哪個檔案需受控驗證；錯誤畫面應能對應實際可恢復步驟（O-77）。
4. **可量測門檻**：O-78 固定 1,000 筆代表資料、10,000 筆壓力資料、查詢與設備，再判定 200ms 目標；編輯器格線與窄視窗斷點依真實資料預覽決定（O-83）。
5. **線框**：審核 [W-01 至 W-08](POC_WIREFRAMES.md) 是否涵蓋 A-01 至 A-14；確認後才進細部視覺設計或實作。MVP 型別、來源網站、閱讀／播放另在各階段決定。
